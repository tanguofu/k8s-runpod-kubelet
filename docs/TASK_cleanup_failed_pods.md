# ТЗ: зомби-pod'ы на virtual-kubelet ноде в проде

## Репозиторий

`~/Desktop/git/opensource/rnpd-kubelet-github` — кастомный virtual-kubelet provider для облачного GPU-провайдера RunPod. Образ деплоится как `ghcr.io/kolpakov-p/runpod-kubelet:latest`. Provider регистрирует фейковую ноду `virtual-runpod` и транслирует жизненный цикл K8s pod ↔ RunPod instance.

## Симптом

В продакшен-кластере (microk8s, k8s 1.33) на ноде `virtual-runpod` накопилось **1635 pod'ов в phase `Failed`** за 12 дней. Все — реплики двух деплойментов (`ml-ocr-main`, `ml-ocr-aux` в namespace `app`). При этом сами деплойменты живые: либо `1/1 Running`, либо scaled `0/0`. Зомби копятся без остановки, кластер забит мусором (`kubectl get pods` лагает, etcd раздут).

## Наблюдения

Status у зомби-pod'ов:
- `status.phase = Failed`, `status.reason = "RunPodDeploymentFailed"` — у большинства
- `status.phase = Failed`, `status.reason = "PodDeleted"` — у меньшинства (~10)

Reason'ы кастомные, выставляются самим provider'ом — не стандартные k8s. По коду они приходят:
- `RunPodDeploymentFailed`: когда RunPod-деплой не удался дольше определённого порога ожидания
- `PodDeleted`: когда инстанс на стороне RunPod пропал, а K8s pod ещё существует

Финалайзеров на pod'ах нет. `deletionTimestamp` не выставлен. ReplicaSet их не подбирает (k8s по дефолту хранит Failed pods для разбора). Pod GC в `kube-controller-manager` управляется `--terminated-pod-gc-threshold` (дефолт 12500) — то есть встроенная чистка проснётся только когда зомби станет >12500. Это не решение, это отложенный взрыв.

## Текущее поведение чистки в provider

В коде есть периодический cleanup-цикл, который занимается:
- Терминированием RunPod-инстансов для исчезнувших K8s pod'ов
- Force-delete pod'ов, застрявших в `Terminating`
- Удалением RunPod-инстансов-сирот без K8s pod'а

Pod'ы в финальном `Failed`-состоянии (живут в K8s, не имеют `deletionTimestamp`) не покрыты ни одной из веток. После перехода в Failed они просто остаются висеть навсегда.

## Что должен сделать provider

Provider — это и есть kubelet виртуальной ноды. По смыслу контракта он отвечает за полный жизненный цикл pod'ов на своей ноде, включая cleanup терминальных состояний. Сейчас он создаёт pod'ы, переводит их в Failed, но не доводит цикл до конца. Это упущенная ответственность.

Цель доработки — закрыть эту дыру так, чтобы Failed-pod'ы на ноде `virtual-runpod` не накапливались бесконтрольно, а уходили из K8s в разумный срок после того, как ясно, что подниматься они не будут.

## Ограничения и контекст для решения

- Не использовать встроенный k8s podGC как костыль (снижение `--terminated-pod-gc-threshold` — это инфра-фикс, не код, делается отдельно).
- Должен быть TTL-буфер между переводом в Failed и удалением. Назначение буфера:
  - Не гонять race с in-flight reconciliation (`notifyFunc`, replicaset controller, virtual-kubelet framework), которая может ещё не успеть обработать только что выставленный Failed.
  - Защита от тайт-лупа при массовом фейле (например, capacity outage на RunPod): без буфера получится шторм `Failed → delete → RS создаёт новый → Failed` с высоким qps по API server и RunPod API.
  - Сохранить K8s Events на pod'е (`kubectl describe pod`) хотя бы на время дефолтного TTL событий — 30 минут — чтобы оператор успел заметить и снять снапшот, если фейлы пошли валом. Сам pod-объект диагностически беден (только generic `Reason`/`Message`), реальные детали лежат в логах `runpod-kubelet` deployment, но Events на pod'е — единственное место с точной хронологией перехода.
- Конкретное значение TTL для этой итерации — **30 минут**.
- Решение должно быть устойчивым к рестарту provider'а: после рестарта накопленный мусор должен начать разгребаться, а не ждать следующей итерации.
- Не дёргать RunPod API ради cleanup'а Failed-pod'ов: для случая когда у Failed pod был привязан RunPod-инстанс, в provider уже есть отдельный механизм очистки сирот на стороне RunPod. Дублировать не надо.
- Поведение перевода pod в Failed (`processPendingPods`, `translateRunPodStatus`) трогать не нужно — корректно, что provider маркирует Failed. Чинится только то, что после маркировки никто не убирает труп.
- Логи через slog-стиль `p.logger.Info/Error/Warn` с полями — как везде в файле. Любые принудительные удаления через существующий хелпер `forceDeleteK8sPod` с осмысленным `reason` для grep'а.
- TTL в этой итерации — константа в коде. Делать его env/CLI-аргументом не нужно, это следующая отдельная задача.

## Out of scope

- Root cause `RunPodDeploymentFailed` (почему деплои фейлятся на стороне RunPod — отдельная история, скорее всего capacity/quota).
- Метрики/Prometheus exposers.
- Конфигурируемость TTL.
- Изменения в kube-controller-manager / microk8s.

## Acceptance criteria

1. `go build ./...`, `go vet ./...`, `gofmt -d` чистые.
2. Существующие тесты проходят. Если в `pkg/virtual_kubelet` уже есть unit-тесты с `fake.NewSimpleClientset` — добавить тест на новый сценарий в том же стиле. Если тестов в пакете нет — оставить без тестов, не вводить новую тестовую инфраструктуру в этом PR.
3. После деплоя в кластер: Failed-pod'ы возрастом старше TTL уходят из K8s в течение одного cleanup-периода. Это видно в логах: новые лог-строки с префиксом, по которому можно легко грепнуть в kibana/loki.
4. Текущие 1635 зомби разгребаются автоматически после деплоя без ручных `kubectl delete`.
5. Активные Running pod'ы (`ml-ocr-main`, `oko-ocr-adapter-olm-deployment`) не должны быть затронуты ни в коде, ни на проде.
6. Если в репе есть Helm chart с `version`/`appVersion` — поднять patch.
